# Cline用プロンプトテンプレート集

## 1. 基本テンプレート

### 1.1 プロジェクト分析開始

```
プロセスエンジニアリング理論効率化システムを使用して、プロジェクト分析を実行してください。

【プロジェクト情報】
- プロジェクトパス: ./[プロジェクト名]
- 現在のフェーズ: [STEP_0_GOAL_DEFINITION | STEP_1_REQUIREMENTS | STEP_2_SYSTEM_DESIGN | STEP_3_DETAILED_DESIGN | STEP_5_DEVELOPMENT_PLANNING | STEP_6_TASK_CREATION | STEP_7_IMPLEMENTATION | STEP_8_CONTINUOUS_IMPROVEMENT]
- チーム規模: [人数]人
- 期限: [YYYY年MM月DD日]
- 技術スタック: [React, Node.js, PostgreSQL等]

【制約条件】
- 最大トークン数: [5000 | 10000 | 15000]
- 緊急度: [LOW | NORMAL | HIGH | CRITICAL]

【特別指定】
- 強制含有理論: [process-essence, quality-principles等]
- 除外理論: [progress-management等]

以下の手順で実行してください:
1. docs2/theory-optimized/metadata/theory-index.yamlを読み込み
2. プロジェクト構造を分析
3. 最適な理論を選択
4. 段階的ロードを実行
5. 推奨事項と実行計画を提示
```

### 1.2 理論の段階的ロード

```
以下の条件で理論の段階的ロードを実行してください:

【即座ロード (核心理論)】
- docs2/theory-optimized/core/process-essence.md
- docs2/theory-optimized/core/quality-principles.md  
- docs2/theory-optimized/core/task-fundamentals.md

【条件付きロード】
プロジェクト特性に応じて以下から選択:
- docs2/theory-optimized/guides/scale-detection.md (規模判定が必要な場合)
- docs2/theory-optimized/guides/category-design.md (中規模以上の場合)
- docs2/theory-optimized/guides/selective-expansion.md (実装フェーズの場合)
- docs2/theory-optimized/guides/progress-management.md (大規模プロジェクトの場合)

【ロード結果の表示】
- 選択された理論とその理由
- 推定トークン使用量
- 適用可能な実装アプローチ
```

## 2. 規模別テンプレート

### 2.1 小規模プロジェクト用

```
【小規模プロジェクト分析】

プロジェクト特性:
- 推定ファイル数: 10未満
- 開発期間: 1-2週間
- チーム規模: 1-2人
- 技術スタック: [シンプルな構成]

使用理論 (約1,000 tokens):
1. process-essence.md - プロセス基本フロー
2. quality-principles.md - 基本品質ゲート
3. task-fundamentals.md - レイヤー単位管理

実装アプローチ:
レイヤー単位管理を採用し、以下の順序で開発:
1. データ層 → 2. ビジネス層 → 3. プレゼンテーション層

品質ゲート:
- ゲート1: 要件完全性 (簡易チェック)
- ゲート4: 実装品質 (基本チェック)
```

```

- 開発期間: 1-3ヶ月
- チーム規模: 3-5人
- 技術スタック: [モダンな構成]

使用理論 (約2,800 tokens):
1. 核心理論 (1,000 tokens)
2. scale-detection.md (800 tokens) - 規模判定手法
3. category-design.md (1,000 tokens) - 機能モジュール設計

実装アプローチ:
機能モジュール単位管理を採用:

【カテゴリ設計】
Category 1: [機能名1] モジュール
├── [サブ機能1]
├── [サブ機能2]
└── [サブ機能3]

Category 2: [機能名2] モジュール
├── [サブ機能1]
├── [サブ機能2]
└── [サブ機能3]

【開発順序】
依存関係分析に基づく並列開発計画を策定
```

### 2.3 大規模プロジェクト用

```
【大規模プロジェクト分析】

プロジェクト特性:
- 推定ファイル数: 30以上
- 開発期間: 3ヶ月以上
- チーム規模: 5人以上
- 技術スタック: [複雑な構成]

使用理論 (段階的ロード):
1. 即座ロード: 核心理論 (1,000 tokens)
2. 条件付きロード: 全実装ガイド (3,000 tokens)
3. オンデマンドロード: 詳細仕様 (必要時)

実装アプローチ:
実装フェーズ単位管理を採用:

【Phase 1: 基盤機能】
- 期間: Week 1-8
- 内容: 認証基盤、DB設計、API基盤、監視基盤

【Phase 2: コア機能】  
- 期間: Week 9-16
- 内容: マスタ管理、基本業務フロー、レポート基盤

【Phase 3: 拡張機能】
- 期間: Week 17-24
- 内容: 高度機能、外部連携、最適化

【品質管理】
全品質ゲートの厳格な運用と継続的監視
```

## 3. フェーズ別テンプレート

### 3.1 要件定義フェーズ (STEP_1)

```
【要件定義フェーズ支援】

現在のフェーズ: STEP_1_REQUIREMENTS

使用理論:
- process-essence.md (プロセス基本フロー)
- quality-principles.md (要件品質ゲート)
- scale-detection.md (プロジェクト規模判定)

実行内容:
1. 要件の完全性チェック
   - 機能要件の網羅性確認
   - 非機能要件の明確化
   - 制約条件の整理

2. プロジェクト規模の判定
   - 基本ファイル数推定
   - 技術・ドメイン複雑度評価
   - 調整係数の適用

3. 品質ゲート1の実行
   - 要件完全性: 100%定義済み
   - 非機能要件明確性: 性能・セキュリティ・運用
   - 制約条件明示: 技術・予算・期間
   - ステークホルダー合意: 承認済み

出力:
- 要件品質評価レポート
- プロジェクト規模判定結果
- 推奨開発アプローチ
```

### 3.2 システム設計フェーズ (STEP_2)

```
【システム設計フェーズ支援】

現在のフェーズ: STEP_2_SYSTEM_DESIGN

使用理論:
- process-essence.md (設計プロセス)
- quality-principles.md (設計品質ゲート)
- category-design.md (アーキテクチャ設計)

実行内容:

   - 技術選択の妥当性検証

2. 品質ゲート2の実行
   - アーキテクチャパターンの適切性
   - 技術選択の妥当性
   - 非機能要件の実現方法
   - 依存関係の明確化

3. 実装計画の策定
   - 開発順序の決定
   - 並列開発の可能性評価
   - リスク要因の特定

出力:
- システムアーキテクチャ設計書
- カテゴリ設計仕様
- 実装計画書
```

### 3.3 実装フェーズ (STEP_7)

## 4. 問題解決テンプレート

### 4.1 トークン制限対応

```
【トークン使用量最適化】

現在の問題: トークン使用量が上限に達している

対応手順:
1. 現在の使用量確認
   - 理論別トークン使用量の表示
   - 効率性の評価

2. 最適化実行
   - 選択的展開レベルの調整
   - 不要理論の除外
   - オンデマンドロードの活用

3. 代替案の提示
   - より軽量な理論の選択
   - フォールバック理論の使用
   - 段階的ロードの調整

実行例:
```
最大トークン数を5000に制限して再分析:
- maxTokens: 5000
- exclude: ["progress-management", "selective-expansion"]
- 展開レベル: 基本のみ
```
```

### 4.2 品質問題対応

```
【品質問題の診断と対応】

現在の問題: [品質ゲート失敗 | バグ多発 | 設計不整合]

診断手順:
1. 品質ゲートの再実行
   - 失敗したゲートの特定
   - 失敗原因の分析
   - 対応策の検討

2. プロセス適合性の確認
   - 理論の適用状況確認
   - 手順の遵守状況評価
   - 改善点の特定

3. 修正計画の策定
   - 優先度付きアクションアイテム
   - 修正スケジュール
   - 再発防止策

出力:
- 品質問題診断レポート
- 修正アクションプラン
- プロセス改善提案
```

### 4.3 スケール変更対応

```
【プロジェクト規模変更への対応】

変更内容: [小規模→中規模 | 中規模→大規模 | 規模縮小]

対応手順:
1. 再分析の実行
   - 新しい規模での理論選択
   - アプローチの変更検討
   - 影響範囲の評価

2. 移行計画の策定
   - 既存成果物の活用方法
   - 新アプローチへの移行手順
   - リスク軽減策

3. チーム体制の調整
   - 役割分担の見直し
   - スキル要件の確認
   - 教育計画の策定

実行例:
```
規模変更に伴う再分析:
- 新しいファイル数: [数値]
- 新しいチーム規模: [数値]人
- 新しい期限: [日付]
- 移行戦略: [段階的 | 一括]
```
```
