# 規模判定ガイド (800 tokens)

## プロジェクト規模判定の基準と手順

### 1. 基本ファイル数推定

#### ファイル数推定手法
**要件ベース推定**:
- 機能要件数 × 1.5 (平均的なファイル/機能比)
- 画面数 × 2-3 (フロントエンド + バックエンド)
- エンティティ数 × 1.2 (モデル + リポジトリ)

**技術スタックベース推定**:
- **Web アプリケーション**: 基本15-20ファイル + 機能数 × 3
- **API サーバー**: 基本10-15ファイル + エンドポイント数 × 2
- **デスクトップアプリ**: 基本20-25ファイル + 画面数 × 4
- **モバイルアプリ**: 基本25-30ファイル + 画面数 × 3

### 2. 複雑度評価の方法

#### 技術複雑度 (1.0-2.0)
**1.0 (低複雑度)**:
- 標準的な技術スタック
- 既知のフレームワーク・ライブラリ
- 単純なアーキテクチャパターン

**1.3 (中複雑度)**:
- 複数技術の組み合わせ
- 新しいフレームワーク・ライブラリ
- マイクロサービスアーキテクチャ

**1.6-2.0 (高複雑度)**:
- 最新・実験的技術の採用
- 複雑な統合要件
- 高度なアーキテクチャパターン

#### ドメイン複雑度 (1.0-2.0)
**1.0 (低複雑度)**:
- 単純なビジネスロジック
- 明確な要件定義
- 標準的な業務フロー

**1.3 (中複雑度)**:
- 複雑なビジネスルール
- 複数システムとの連携
- 規制・コンプライアンス要件

**1.6-2.0 (高複雑度)**:
- 高度なアルゴリズム要求
- リアルタイム処理要件
- 複雑な承認・ワークフロー

#### チーム係数 (0.8-1.5)
**0.8 (経験豊富)**:
- 技術・ドメインに精通
- チーム連携が良好
- 過去の類似プロジェクト経験

**1.0 (標準)**:
- 一般的なスキルレベル
- 標準的なチーム構成
- 適度なプロジェクト経験

**1.2-1.5 (経験不足)**:
- 新技術・新ドメイン
- チーム結成直後
- 初回プロジェクト

### 3. 調整係数の適用

#### 計算式
```
調整後ファイル数 = 基本推定ファイル数 × 技術複雑度 × ドメイン複雑度 × チーム係数
```

#### 適用例
**例1: 中規模Webアプリケーション**
- 基本推定: 20ファイル
- 技術複雑度: 1.2 (React + Node.js)
- ドメイン複雑度: 1.3 (ECサイト)
- チーム係数: 1.0 (標準チーム)
- 調整後: 20 × 1.2 × 1.3 × 1.0 = 31.2 → **大規模**

**例2: 小規模API**
- 基本推定: 8ファイル
- 技術複雑度: 1.0 (Express.js)
- ドメイン複雑度: 1.0 (CRUD API)
- チーム係数: 0.9 (経験チーム)
- 調整後: 8 × 1.0 × 1.0 × 0.9 = 7.2 → **小規模**

### 4. 規模別管理アプローチ

#### 小規模 (< 10ファイル): レイヤー単位管理
- **特徴**: シンプルな構造、少ない依存関係
- **管理単位**: プレゼンテーション層、ビジネス層、データ層
- **開発順序**: 下位層から上位層へ順次開発

#### 中規模 (10-30ファイル): 機能モジュール単位管理
- **特徴**: 複数機能、モジュール間連携
- **管理単位**: ユーザー管理、商品管理、注文管理等
- **開発順序**: 独立性の高いモジュールから並列開発

#### 大規模 (> 30ファイル): 実装フェーズ単位管理
- **特徴**: 複雑な依存関係、多数のコンポーネント
- **管理単位**: 基盤機能、コア機能、拡張機能
- **開発順序**: 段階的リリース、継続的統合
